# 文档撰写指南

> 这份文件是 `docs/` 文档区的**唯一权威说明**，合并并取代了原先的《文档领域规划》与《写作风格规范》。
> 位置：`docs/_plan/`（以 `_` 开头，构建期自动忽略，不会出现在站点上）。
> 适用对象：在这个仓库里写文档区内容的任何人或子智能体。

---

## 0. 目录结构约定

```
docs/
├─ <领域>/                 一级：一个可独立成篇的技术领域/工具
│  └─ <单元>/              二级：一个文件夹 = 一个主题页 = 站点一页
│     ├─ 01-第一个文件.md   三级：文件，按文件名升序拼进同一页
│     ├─ 02-第二个文件.md
│     └─ fig-1.png         图片与 md 放一起，用 ![](./fig-1.png) 引用
```

要点：

- **领域 = 一个具体的技术名词/工具/子领域**（FreeRTOS、CAN 通信、MuJoCo 与 MJX、nginx 配置）；不要用"机器人控制""AI 工具链"这种能力块或项目分组。
- **单元 = 该技术的子主题**，能独立成篇（一个单元建议 3–6 个文件）。工程细节（CRC16、DWT、ImuTempControl、裁判系统…）是**单元或文件**，不是领域。
- 排序：领域/单元/文件都按名字的 `01-` 数字前缀升序；没有前缀的排在后面（同序按拼音）。
- 展示名会自动剥掉数字前缀；要改展示名而不改 URL，在 frontmatter 写 `domain:` / `unit:`。
- 以 `_` 或 `. ` 开头的文件/文件夹一律忽略（本目录就是靠这个隐藏的）。
- md 必须正好在 `docs/<领域>/<单元>/` 这一层；更深的目录不会被当成单元。
- 领域页只统计 md 文件：**空文件夹不会出现在站点上**，所以别建空壳占位。
- 数字前缀用于**排序分块**（站点没有"大类"层，同块领域会挨着排）。

### frontmatter（全部可选，但这些建议写全）

```yaml
---
title: 显示标题          # 默认取第一个 H1，再默认取文件名
summary: 一句话摘要       # 显示在领域页的单元列表
tags: [FreeRTOS, 任务调度]
updated: 2026-10-07      # 用于单元头部与"最近更新"
---
```

### 内容写法支持

- GFM：表格、任务列表、删除线、脚注
- 公式：行内 `$...$`、块级 `$$...$$`（KaTeX，构建期渲染）
- 图表：```mermaid 代码块（浏览器端懒加载渲染；关掉 JS 显示源码）
- 代码：Shiki 高亮 + 一键复制，**必须标语言**
- 图片：点击放大、自动图注

### 一个坑

文档 md 里的**裸站内链接不会自动加 `base`**（站点部署在 `/tc63`）。跨到作品页要写全 `/tc63/projects/xxx/`，或干脆只写文字引用。

## 2. 写作风格规范（去 AI 腔）

### 2.1 目标

读起来像工程师写给同事的内部技术笔记：陈述为主、信息密度高、不表演、不抒情、不反复强调"这很重要"。
判断标准：**把任何一句话单独摘出来，不应该出现"只有 AI 会这么写"的痕迹。**

### 2.2 禁用句式

| 句式 | 例 | 改法 |
| --- | --- | --- |
| 不是……而是…… | "不是背配置，而是能回答……" | 直陈结论，或拆两句："要能回答……。背配置没用。" |
| 并非……而是…… | 同上 | 同上 |
| 与其说……不如说…… | —— | 删掉评价，直陈事实 |
| 设问开头 | "为什么中断版要返回值？" | 改陈述句："中断版需要返回值，因为……" |
| 元叙述 | "本章最需要照代码说话的一节""摊开看""把视野拉远" | 删掉，直接进入内容 |
| 命令式口头禅 | "记住这个数""值得逐条记住" | 删掉"记住"，把结论写出来 |
| 评价填充 | "非常值得优先怀疑的方向""值得肯定的地方" | 写"优先怀疑的方向""可取的做法是" |

### 2.3 禁用词表（正文中不出现）

比喻与情绪词：`刺眼` `尖锐` `地雷` `手滑` `翻车` `体检` `尸体` `标本` `解剖` `裸奔` `裸` `一把梭` `稳如` `血腥` `致命` `杀手` `惊艳` `漂亮` `硬核` `狠`

| 原词 | 改用 |
| --- | --- |
| 陷阱 / 坑 | 易错点、问题、风险 |
| 体检 | 检查、排查 |
| 账 / 堆账 | 核算、预算、占用 |
| 标本 | 例子、样本 |
| 裸奔 / 裸 | 无保护、直接访问 |
| 翻车 | 失败、出错 |
| 地雷 | 隐患 |
| 手滑 | 笔误、写错 |
| 致命 | 严重 |

（`陷阱` 允许出现在小节标题里，如"常见陷阱与调试"，正文中不用。）

其他要压掉的词：`一句话` `说白了` `换句话说` `其实` `本质上` `恰恰` `真正` `摊开` `值得` `记住` `本章` `本篇`。
其中 `其实`/`真正`/`恰恰` 每篇最多各留 1 处，且必须承载信息。

### 2.4 加粗规则

几乎每个断言都加粗，读起来全是重点，等于没有重点。

- **允许**：代码标识符、配置项名、文件名、函数名、寄存器名；术语**首次**出现；表格表头关键字段。
- **禁止**：整句加粗、行首加粗引导句（`**注意最后三项**`）、评价性加粗（`**极其关键**` `**代价**`）。
- 要强调就改句子结构（结论放句首或句尾），不要用加粗。
- 目标：**每篇加粗不超过 10 处**。

### 2.5 标点与人称

- 破折号 `——` 每篇不超过 8 处；能用逗号、冒号、句号就别用破折号。
- 少用第二人称"你"；确需对读者说话时用"需要……""应当……""注意……"。
- 感叹号、省略号、emoji：正文不用。

### 2.6 鼓励的写法

- 陈述句为主，主语尽量是"本工程 / 该函数 / 这个值 / 两块板"。
- 一句一个信息点；不写排比，不写三连句。
- 结论先行，再给依据（源码行号、实测数字）。
- 对比用表格，流程与关系用 Mermaid，推导用公式。

## 3. 内容要求

### 3.1 每个文件的结构

概念 → 机制/原理 → **落到本项目**（必须附源码路径与行号）→ 易错点 → 小结（核心概念 + 设计权衡表）→ 练习（基础题 / 挑战题）→ 附：本页引用的固件路径。

### 3.2 图：一律 Mermaid

禁止 ASCII/文字画图。选型：

| 用途 | 图类型 |
| --- | --- |
| 流程、拓扑、时钟树、数据流 | `flowchart TD` |
| 时序、中断、报文交互、优先级反转 | `sequenceDiagram` |
| 状态机、引脚模式、协议状态 | `stateDiagram-v2` |

节点标注用中文；每篇至少 2 张图。

### 3.3 事实必须来自源码

- 数字、行号、配置值都要能指回具体文件（例：`Core/Src/freertos.c:114`）。
- 代码注释里的说法与实现不一致时**以代码为准**，并把"文档 vs 代码"的冲突显式标成待现场确认。
- 推断、未实测、依赖器件规格的内容必须在正文标注（"待实测""按手册""属推断"），不能写成结论。
- 不编造 API 用法：本工程没用的原语就写"本工程未使用 + 若要使用该怎么写"。

### 3.4 每单元规模

3–6 个 md；每篇 150–400 行。起步阶段允许一个单元只有 1 个文件。

## 4. 派发子智能体的流程

1. **一个子智能体写一个单元**，写入互不重叠的目录；同一领域的兄弟单元并行时，必须在任务卡里给出**统一口径**（拓扑、ID、优先级等），否则会各写一套。
2. 先做主智能体侦察：把要引用的真实数值、路径、易错点写进任务卡，减少子智能体猜错。
3. 平台**并发上限 8 个子智能体**；超过要分两批（等前一批结束再派）。
4. 任务卡必须包含：目标目录、建议文件清单、素材路径、已核实事实、写作规范引用、硬性要求、交付回报格式。
5. 子智能体**不要跑 `npm run build`**（并发构建会互相覆盖 `dist/`），由主智能体统一构建。
6. 子智能体写完后自检 Mermaid：`node docs/_plan/check-mermaid.mjs "<目录>"`，必须 `failed: 0`。

任务卡模板：

```
【背景】个人网站仓库 /home/wyx/TC63PersonalWebsite，文档区三级结构…
【必须遵守】先读 docs/_plan/文档撰写指南.md 的第 2、3 节并逐条执行
【素材来源】列出固件/仓库路径，必读文件
【已核实事实】把关键数值、路径、已知纠错列出来
【硬性要求】每篇 ≥2 张 Mermaid；frontmatter 四字段；数字前缀命名；只写本目录；不跑 build
【交付】文件清单（行数）、Mermaid 数、加粗/破折号/禁用词自检数字、引用的路径、标注的不确定项
```

## 5. 验收清单（主智能体）

1. `npm run build` 通过，文档页数量符合预期。
2. `node docs/_plan/check-mermaid.mjs docs/<领域>` 通过（`failed: 0`）。
3. 风格自检（见 5.1）：加粗 ≤10/篇、破折号 ≤8/篇、`不是…而是` = 0、禁用词正文 0。
4. **跨单元一致性**：同一事实（拓扑、ID、优先级、周期）在不同单元里必须一致；有冲突就回源码判定并统一改写。
5. 抽查：关键数字仍存在、代码块未被改动、没有 ASCII 图。

### 5.1 风格自检脚本

```bash
DIR="docs/01-FreeRTOS"   # 换成要查的领域
for f in $(find "$DIR" -name '*.md' | sort); do
  printf "%-46s bold=%s dash=%s erShi=%s bad=%s\n" "$(basename "$f")" \
    "$(grep -o '\*\*' "$f" | wc -l)" \
    "$(grep -o '——' "$f" | wc -l)" \
    "$(grep -oE '不是[^。；]{0,30}而是' "$f" | wc -l)" \
    "$(grep -oE '陷阱|坑|体检|裸|翻车|地雷|手滑|摊开|一句话|值得|本章|本篇' "$f" | wc -l)"
done
```

硬指标：`不是…而是` = 0；加粗 ≤10/篇；破折号 ≤8/篇；禁用词正文 0；`本章`/`本篇` = 0。

写作时核实出、并已写进文档的真实缺陷（供后续单元复用）：

- `freertos.c:134` 的 `StartTestTask_Init()` 被注释，运行期是 7 个任务实例；`osPriorityNormal` 映射到 FreeRTOS 优先级 3。
- heap_4 真实可用 40944 B（不是 40960）；6 任务 + 1 队列占 28456 B。
- `configCHECK_FOR_STACK_OVERFLOW` 与 `INCLUDE_uxTaskGetStackHighWaterMark` 都没开；`Debug_vars` 的 9 个变量被 `--gc-sections` 全部回收。
- `ImuTempControl` 的占空比恒为 100%（`compare = Period×duty` 没除满量程）；TIM10 跑 33.6 kHz PWM 但不产生中断。
- LK/pitch 在**云台板 CAN1**（0x141 发、0x181 收），`项目概述.md` 写的 CAN2 有误；底盘板那套 LK 函数无调用点。
- yaw 占 `0x1FF` 第 1 槽、反馈 0x205：按 GM6020 是 ID1，按 M3508 是 ID5（同槽同反馈）；代码沿用 M3508 编号记 `motor_5`。
- 底盘 `case 0x301` 缺 `break` 落穿到 `0x302`；底盘 `total_angle` 是 `int16_t`（约 ±4 圈回绕）；底盘速度环积分限幅被注释。
- `0x2FF` 只填 6 字节而 DLC=8；底盘全局符号 `chassis` 定义 2 字节却按 56 字节使用。
- `motor_power_control.c` 正/反向方程对 `k1·w` 用法不一致；裁判 `0x0201/0x0202` 字段只写不读，限值硬编码 95.0f。
- 工作记录把 CAN `ErrorCode=0x00200000` 记成 `NOT_STARTED`，实际是 `HAL_CAN_ERROR_PARAM`。
