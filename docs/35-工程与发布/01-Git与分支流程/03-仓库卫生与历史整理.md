# 仓库卫生与历史整理

仓库用久了会出现一些与代码无关的东西：编译缓存、工具生成的会话状态、同一个文件的几份副本、甚至别人项目的完整仓库。它们在 `git status` 里不显眼，却会把仓库撑到几百 MB，让克隆、备份与日常扫描一起变慢。判断这些内容该不该留在版本库里，是这一篇要解决的核心问题。

这篇按"先看清楚、再决定处置、最后才是改写历史"的顺序，讲清 `git rm --cached`、`.gitignore`、`git mv` 与历史改写各自解决什么，以及哪些操作一旦执行就很难回头。

## 什么该提交，什么不该提交

判断标准只有一条：这份内容在别人克隆之后会不会被**直接使用**。会被直接使用的源码、配置与文档应当入仓；只在构建或运行时生成、又能随时重建的内容应当排除。按类别套用，常见情况各有明确口径：

| 类别 | 典型内容 | 该不该入仓 | 判断理由 |
| --- | --- | --- | --- |
| 源码与文档 | 代码、脚本、README | 入仓 | 克隆后直接使用，无法重建 |
| 依赖 | `node_modules/`、`.venv/`、`vendor/` | 排除 | 由清单文件重建，体积大且与平台相关 |
| 生成物 | 构建输出、编译中间件 | 看有无下游 | 别人能自行构建则排除；部署直接消费它才入仓 |
| 缓存与运行态 | `.cache/`、会话状态、日志 | 排除 | 纯副作用，重建即可，且常含本机路径 |
| 密钥与凭据 | `.env`、`*.pem`、token | 排除，并按已泄漏处理 | 一旦进历史就随克隆扩散，撤销比删除可靠 |
| 大文件与数据 | 数据集、模型权重、二进制 | 一般排除 | 用大文件存储或独立备份，把版本库与数据分离 |
| 内嵌仓库 | 别人项目的完整 `.git` | 排除或改子模块 | 直接复制会丢内层历史，或被外层仓库拒绝跟踪 |

这条标准要先于「怎么清理」决定：一开始就判对，后面根本不需要改写历史。

## 误提交是怎么发生的

`.gitignore` 只对**未被跟踪**的文件生效，这是误提交的根源。一个目录如果在写出忽略规则之前就已经被 `git add` 过，之后即使补上规则，它仍然留在版本控制里——规则不会追溯撤销已经跟踪的条目。另一处常见漏洞是规则写得太窄：只忽略了某个子目录，根级同类目录照旧暴露（本项目的知识库仓库就同时踩中过这两种）。

判断方法是把"工作区里存在"与"被仓库跟踪"分开看：`git status --ignored` 看忽略状态，`git ls-files 目录` 看跟踪状态。后者才是提交体积的来源。

```mermaid
flowchart TD
  A["发现仓库很大"] --> B{"文件是否被跟踪"}
  B -- "否" --> C["补 .gitignore 即可"]
  B -- "是" --> D{"是否还需要保留"}
  D -- "不需要" --> E["git rm -r --cached 后补忽略规则"]
  D -- "需要但要移动" --> F["git mv 保留历史"]
  E --> G["提交"]
  F --> G
  G --> H{"体积仍大吗"}
  H -- "是" --> I["考虑历史改写并评估影响"]
  H -- "否" --> J["结束"]
```

## 三个操作各解决什么

| 操作 | 作用 | 适用场景 |
| --- | --- | --- |
| `git rm -r --cached 目录` | 停止跟踪但保留工作区文件 | 缓存、生成物、误提交的目录 |
| 补 `.gitignore` | 阻止再次被添加 | 与上一步配套 |
| `git mv 旧 新` | 移动文件并保留历史 | 目录重组、成果归档 |
| `git rm -r 目录` | 删除文件并停止跟踪 | 确认不再需要的重复副本 |
| 历史改写工具 | 从所有历史中移除大文件 | 体积仍无法接受时 |

前四个操作只影响最新提交，历史里仍然留着那些文件。要把体积降下来，必须改写历史，这一步的影响面比前四步大得多。

停止跟踪不等于删除。`git rm -r --cached` 之后文件仍在工作区，本地开发不受影响；如果某台机器上有人正在使用这些路径，也不会因为这次提交而消失。变化的只是仓库内容与克隆体积的走向。

这里的「跟踪」指索引（index，也叫暂存区）：改动先发生在工作区，`git add` 把内容写进索引，`git commit` 再把索引整体固化成一次提交，顺序是「工作区 → 索引 → 提交」。因此 `git rm -r --cached` 只把条目从索引里拿掉，工作区文件原样留着；不带 `--cached` 的 `git rm` 才会连工作区一起删。

## 目录重组为什么用 git mv

目录重组时用 `git mv` 而不是普通 `mv`，原因是保留历史：普通 `mv` 加 `git add` 在 git 眼里是一次删除加一次新增，`git log --follow` 也追不到之前的内容；`git mv` 记录成重命名，历史链保持完整。这条差别在文件被移动之后还会长期起作用——只要有人需要回溯这段内容的来历，没有重命名记录就会断在搬迁那一刻。

重组还会遇到内嵌仓库的问题：如果某个子目录本身是一个独立的 git 仓库，直接移动会让它变成普通目录（丢失内层历史），或者被外层仓库拒绝跟踪。常见处理是抽成子模块，或者先把内层仓库的历史导出再合并，具体方式取决于这些项目是否还需要独立维护。

## 历史重写的风险与顺序

改写历史会改变提交号，进而影响所有已经克隆过仓库的环境，至少有四处：本机的工作副本、远程仓库、任何已经拉取过的机器，以及基于这些提交号写下的记录（发布标签、部署日志、引用某次提交的文档）。已经推送的分支再被改写，其他人无法直接拉取，只能重新克隆或做手术式修复。

如果确实要改写，顺序是：先把要保留的数据导出留档，再在本地完成改写，确认仓库能正常构建与测试，然后强推远程，最后通知所有克隆过的人重新拉取。强推是这条链里唯一不可逆的动作，执行前应当确认远程没有别人正在推送。

```mermaid
flowchart LR
  P["确认误提交范围"] --> A["git rm --cached 与忽略规则"]
  A --> B["提交并验证仓库可用"]
  B --> C{"体积是否可接受"}
  C -- "是" --> D["结束 保留历史"]
  C -- "否" --> E["本地历史改写"]
  E --> F["全量验证 构建与测试"]
  F --> G["强推远程"]
  G --> H["通知其他克隆重新拉取"]
```

## 重复副本为什么要单独处理

还有一类容易被忽略的问题是重复副本：同一个文件在多个目录下内容完全相同。重复的害处不在体积，而在维护——改一处忘另一处，下一次读文档时不知道哪一份才作数，结论会随「读到哪一份」而变。处理时只保留一份，其余归档或删除，并在提交信息里写清保留哪一份、为什么。

## 忽略规则的写法与验证

忽略规则的写法有个常见顺序问题：先补规则、再确认状态、最后才提交。规则里应当区分"忽略目录内容"与"保留目录本身"，前者用 `目录/` 结尾，后者需要额外的占位文件。规则写完之后用 `git status --ignored` 确认目标已经被忽略，再用 `git ls-files` 确认它不在跟踪列表里。两步都通过，才说明清理完成。

验证还要覆盖反例：故意在缓存目录里新建一个文件，看它是否仍然不出现。规则没有生效时往往是因为上一层目录被整体忽略了，此时需要显式取消忽略某个子路径。

## 克隆与备份的成本

仓库体积的直接代价出现在三处：新机器克隆、远程仓库备份、以及每次 `git status` 与 `git log` 的扫描。几个几百 MB 的历史无关目录长期存在，就等于每次克隆都要把它们搬一遍——而且这份成本会平摊到每一个后来者身上。

判断标准可以简化为一句：这部分内容在克隆之后会不会被用到。不会被用到的缓存与会话状态属于可以清理的部分；需要长期保留的原始数据则适合放到仓库之外单独备份，或者使用大文件存储方案，把版本库与数据分离。

生成物要分两类看，这是最容易判错的一处。部署流程直接消费的产物可以有意入仓：本项目的站点仓库就把构建结果留在版本库里，服务器只 `git pull`、不在服务器上装依赖再构建。纯副作用的缓存与运行态则应当移除。同样是「生成物」，判断依据是它有没有下游使用者——有下游就入仓，没有就排除。

下面是一份真实 `.gitignore`（节选）：排除项逐行列出，并用注释说明为什么独独放行 `dist/`。这种「把判断写进文件」的做法本身值得学——几个月后不会有人记得当初为什么这么配。

```gitignore
# TC63PersonalWebsite/.gitignore（节选）
node_modules/
.astro/
.preview/
.npm-cache/
.env

# dist/ 故意不忽略：
# 服务器部署 = 本地构建 → git push main → 服务器只 git pull
```

语法上，以 `/` 结尾的模式只匹配目录，`*` 是通配符，`!` 开头的行用来反向取消一条已有忽略规则。

判断某个目录该不该入仓，可以问它是否会被克隆之后的机器直接使用。会被直接使用的产物、配置与文档应当入仓；只在构建或运行时生成、又能随时重建的内容应当排除。按这条标准过一遍目录树，多数误提交都能自己浮出来。

仓库卫生是每次新增工具时顺手确认的一件事，而不是一次性的清理任务：新目录产生的中间文件有没有被忽略规则覆盖。把它当成提交前的习惯，就不会再积累出需要改写历史才能解决的局面。

清理完成之后还要回看一次忽略规则本身。规则写得过宽会误伤需要入仓的文件，写得过窄又会漏掉新生成的中间状态；每次处理完一处误提交，顺便确认相邻路径的规则是否也该调整，比事后一次性重写更省力。

## 常见判断偏差

| # | 判断偏差 | 表现 | 依据 |
| --- | --- | --- | --- |
| 1 | 加了忽略规则就以为文件不再进仓库 | 目录仍在跟踪列表里 | 已跟踪文件不受 `.gitignore` 影响 |
| 2 | 用普通 mv 搬迁目录 | 历史断在搬迁处 | `git mv` 才保留重命名记录 |
| 3 | 以为删除文件就会减小仓库 | 克隆体积不变 | 体积来自历史，需要改写才能释放 |
| 4 | 直接强推改写后的历史 | 其他克隆报错 | 提交号变化影响所有副本 |
| 5 | 忽略内嵌 git 仓库 | 目录被当作普通文件或拒绝提交 | 需要子模块或历史导出 |
| 6 | 保留两份内容相同的文件 | 后续修改只落到一份 | 重复副本带来维护歧义 |

## 小结

### 核心概念

- 已跟踪的文件不会因为新增忽略规则而离开版本控制，需要 `git rm --cached`。
- 判断体积来源要看跟踪列表而不是工作区大小。
- `git mv` 保留重命名历史，是目录重组时的正确做法。
- 删除文件只影响最新提交，减小克隆体积需要改写历史。
- 历史改写会改变提交号，强推前要确认影响到的克隆与协作者。
- 重复副本的主要成本是维护歧义，处理时只保留一份。

### 设计权衡

| 权衡点 | 常见选择 | 收益与代价 |
| --- | --- | --- |
| 清理方式 | 先 `rm --cached` 加忽略，再评估改写 | 风险可控；代价是体积不会立刻下降 |
| 目录重组 | 统一用 `git mv` | 历史完整；代价是操作前要确认目标路径 |
| 内嵌仓库 | 评估后再决定子模块或导出 | 各自历史得以保留；代价是需要额外维护 |
| 历史改写 | 谨慎执行、全量验证后强推 | 体积彻底下降；代价是不可逆与协作成本 |
