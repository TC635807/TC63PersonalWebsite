# 关节与执行器

关节给 body 增加自由度，执行器给自由度施加广义力。这两件事在 MJCF 里分属两个段，在 MjModel 里分属两个数组，在物理求解里则汇合到同一个方程。Go1 的 13 个关节里只有 12 个受执行器驱动，基座完全靠重力和接触受力，这条不对称是所有动作语义讨论的起点。

执行器顺序一旦与关节顺序、观测切片错开，策略输出的动作就会加到别的关节上，这类错误在数值上只表现为性能下降。位置伺服编译后的力律、三组执行器的行程与力矩上限，以及从策略输出到 qpos 推进的完整链路，是判断动作语义是否一致的三份依据。

> 关节与执行器定义在 `models/go1/go1_mjx_position.xml` 与 ；动作到 ctrl 的映射在 `envs/go1_walk.py` 与 `envs/go1_getup.py`。

## 1. 关节给自由度，执行器给力

Go1 两种关节：

| 关节 | 数量 | 自由度 | 位置 |
| --- | --- | --- | --- |
| free joint | 1 | 平移 3 + 旋转 3 | trunk，`models/go1/go1_mjx_position.xml` |
| hinge | 12 | 每个 1 个转角 | 每条腿 hip / thigh / calf，`models/go1/go1_mjx_position.xml,119,126` 等 |

三种执行器语义对比：

| 类型 | 输入含义 | 输出力 | 本项目使用 |
| --- | --- | --- | --- |
| `position` | 目标关节角 | `kp*(ctrl-q) - kv*qdot` | 是，12 个 |
| `motor` | 直接力矩 | 与 ctrl 成比例 | 参考仓库的 torque 模型 |
| `general` | 自定义 | `gain*act + bias` | 否 |

执行器数量等于受控关节数，本仓库 $nu=12$，与 12 个铰链一一对应；free joint 不在其中。

位置伺服把「目标角」变成「力矩」。策略输出的是角度目标，力矩由伺服按增益算出，这个换算关系决定了 RL 动作的物理含义。

控制周期与物理步长分离。`envs/go1_walk.py` 定义 `ctrl_dt=0.02`、`sim_dt=0.002`，一个控制步含 10 个物理子步；`sim/getup_keyframe.py` 也用 0.02 s 作控制步。ctrl 在一个控制步内保持不变，执行器按子步持续出力。

## 2. 位置伺服编译成固定增益与仿射偏置

MuJoCo 的位置执行器编译后是固定增益 + 仿射偏置。本项目实测 `actuator_gainprm = [20, 0, ...]`、`actuator_biasprm = [0, -20, -1, ...]`、`gear = 1`，因此第 $i$ 个执行器的关节力矩：

$$\tau_i = \mathrm{clip}\big(k_p (u_i - q_i) - k_v \dot{q}_i,\ -f_{\max},\ f_{\max}\big)$$

其中 $u_i$ 是 ctrl，$k_p=20$、$k_v=1$，$q_i$、$\dot{q}_i$ 从 qpos[7:]/qvel[6:] 取。`ctrlrange` 先夹 ctrl，`forcerange` 再夹力矩。trunk 没有执行器，它靠重力和接触受力。

三组执行器的行程与力矩上限：

| 组 | ctrlrange (rad) | forcerange (N·m) |
| --- | --- | --- |
| hip（abduction 类） | -0.863 .. 0.863 | 正负 23.7 |
| thigh（hip 类） | -0.686 .. 4.501 | 正负 23.7 |
| calf（knee 类） | -2.818 .. -0.888 | 正负 35.55 |

`actuator_gainprm` 与 `actuator_biasprm` 是编译产物，读它们可以确认伺服参数确实来自 XML 的 default 而不是内置默认：本项目实测 gainprm 首项 20、biasprm 前三项 0、-20、-1，与 `kp=20`、`kv=1` 对应。

关节自身还有三项动力学参数：`damping=1.0`（粘滞）、`armature=0.01`（转子惯量）、`frictionloss=0.1`（库仑摩擦）。它们与伺服力一起进入 $M\ddot q + \tau_{bias} = \tau_{act}$ 的求解，因此单纯提高 $k_p$ 只改变跟踪刚度，不改变可达行程。

两个夹紧点的顺序也要记住：ctrlrange 在环境的 `step` 里生效，forcerange 在 MuJoCo 求解器里生效。策略输出超出 ctrlrange 时行为不报错、只是被夹住，这是动作饱和最常见的表现。

## 3. 一步的完整链路与 10 个子步

```mermaid
flowchart TD
  A["策略输出 12 维 action"] --> B{"动作语义"}
  B -->|走路：绝对| C["clip(action, ctrl_lo, ctrl_hi)"]
  B -->|起身：增量| D["clip(qpos[7:] + 0.5*action, ctrl_lo, ctrl_hi)"]
  C --> E["mjx_env.step 得到 data.ctrl"]
  D --> E
  E --> F["位置伺服 tau = kp(ctrl-q) - kv*qd"]
  F --> G["forcerange 饱和"]
  G --> H["qacc / qvel / qpos 推进 n_substeps 次"]
````

```mermaid
sequenceDiagram
  autonumber
  participant P as 策略
  participant E as env.step
  participant S as mjx 求解器
  P->>E: action (12,)
  E->>E: clip 到 ctrlrange
  E->>S: mjx_env.step(model, data, ctrl, n_substeps)
  S->>S: 子步 1 到 n，每步重力与接触与伺服积分
  S-->>E: 新 data
  E-->>P: obs, reward, done
````

`ctrl_dt` 与 `sim_dt` 的比值要能整除，否则子步数取整会让实际控制周期偏移。本仓库 0.02 / 0.002 正好是 10。

一次控制步展开成 10 个物理子步，$n_{\text{sub}} = 0.02 / 0.002 = 10$。子步之间 ctrl 恒定，所以策略发出的目标在 20 ms 内一直有效；这条性质让"动作平滑"与"低通滤波"成为两个独立的手段：前者改目标，后者改目标的变化率。

## 4. 走路与起身的动作落点

| 位置 | 内容 | 与原理的对应 |
| --- | --- | --- |
| `models/go1/go1_mjx_position.xml` | `<position kp="20" kv="1" forcerange="-23.7 23.7"/>` | 三类关节的公共伺服增益 |
| `models/go1/go1_mjx_position.xml` | knee 的 `forcerange="-35.55 35.55" ctrlrange="-2.818 -0.888"` | 小腿行程与力矩上限 |
| `models/go1/go1_mjx_position.xml` | `<freejoint/>` | 无执行器的 6 自由度基座 |
| `models/go1/go1_mjx_position.xml,119,126` | abduction / hip / knee 的 `class` | 关节限位来自 default 子类 |
| `models/go1/go1_mjx_position.xml` | 12 个 `<position ... joint="...">` | 关节与执行器一一对应 |
| `envs/go1_walk.py` | `opt.timestep=sim_dt`、`ccd_iterations=20` | 子步时长与连续碰撞检测 |
| `envs/go1_walk.py` | `jp.clip(action, ctrlrange[:,0], ctrlrange[:,1])` | 走路绝对动作语义 |
| `envs/go1_walk.py` | `mjx_env.step(..., motor_targets, self.n_substeps)` | 一次控制步展开为多个物理子步 |
| `envs/go1_getup.py` | `target = qpos[7:] + action*0.5` | 起身增量动作语义 |
| `envs/go1_getup_v2.py` | `target = default_pose + 0.5*a_f` | 另一版以名义站姿为锚的增量 |
| `sim/getup_keyframe.py` | `HOME`、`CTRL_LO`、`CTRL_HI` 常量 | 状态机直接用 ctrlrange 端点发力 |
| `models/go1/go1_mjx_position.xml` | `damping/armature/frictionloss` | 关节自身的动力学，与伺服增益叠加 |

起身两版的锚点不同：`envs/go1_getup.py` 以当前关节角为锚，`envs/go1_getup_v2.py` 以 keyframe 的名义站姿为锚并配动作滤波。前者对任意摔倒姿态都温和，后者把可达范围限制在名义站姿正负 1.5 rad，接近参考的公开配方。

走路与起身的差别只在动作语义。`envs/go1_walk.py` 记录了早期版本把动作从 $[-1,1]$ 仿射映射到 ctrlrange，零动作落在行程中点，初始策略一上来就把 hip 目标推到 1.9 rad，关节速度约 7 rad/s，奖励被成本压住。改成直接输出 ctrl 目标后才有非零回报。

## 5. 执行器顺序与关节顺序、观测切片的一致性

执行器的排列顺序与关节顺序、`envs/go1_walk.py` 里按腿 reshape 的 qpos 切片、观测维度三者一致。任何一处重排都要同时改这四处，否则动作会打到错误的关节上。四者的顺序在编译后由 `nu=12` 与 actuator 段的行序共同固定。

`envs/go1_walk.py` 的切片按腿分块，每块三个关节的顺序与执行器顺序一致。观测里若含关节角与关节速度，切片顺序也必须相同，否则策略看到的 q 与它输出的目标不在同一坐标系。

这条约束的来源是 MJCF 的编译约定：关节按出现顺序编号，执行器也按出现顺序编号，两者都写进 MjModel 数组。环境代码按固定切片取 qpos[7:19]，因此腿的顺序、执行器的顺序、动作向量的分块三者必须同步。

## 6. 动作语义改动前后的对照

走路动作语义从"仿射映射到 ctrlrange"改成"直接输出 ctrl 目标"是这一页影响最大的一次改动，两版在同一个初始策略下的差别可以直接量出来：

| 版本 | 零动作对应的 hip 目标 | 初始关节速度 | 早期回报 |
| --- | --- | --- | --- |
| 仿射映射 | 约 1.9 rad（行程中点） | 约 7 rad/s | 被成本项压住，长期为零 |
| 直接输出 ctrl | 0 rad（贴住软限位） | 接近零 | 出现非零回报 |

根因是零动作的含义：仿射映射把 $a=0$ 映到行程中点，而 hip 行程 -0.686 到 4.501 的中点接近 1.9 rad，与站立姿态差距很大。改成语义直连后零动作等于零目标，初始策略不会主动甩关节，探索从温和状态开始。

起身两版可以做同样的对照：`envs/go1_getup.py` 的锚是当前角，`envs/go1_getup_v2.py` 的锚是名义站姿。前者对摔倒姿态更宽容，后者可达范围受名义站姿限制。选哪一版取决于任务是否需要从任意姿态恢复。

## 7. 关节与执行器相关的故障现象

| 现象 | 原因 | 对应位置 |
| --- | --- | --- |
| 把 `kv` 与关节 `damping` 当同一个量 | 两处都在耗能，调一个不够 | `models/go1/go1_mjx_position.xml` 与  |
| 动作当成力矩 | 位置模型下输出被解释为目标角 | `models/go1/go1_mjx_position.xml` 是 position 而非 motor |
| 忘记 ctrl 会被夹 | 策略输出超程但行为不变 | `envs/go1_walk.py` |
| 以为抬 kp 能解决行程不足 | 力矩先顶到 forcerange 饱和 | `models/go1/go1_mjx_position.xml`，`docs/experiment-log.md` |
| 动作单位用度 | ctrlrange 是弧度 | `models/go1/go1_mjx_position.xml,32,36` |
| 起身用绝对目标 | 随机初始策略把机器人甩飞 | `envs/go1_getup.py` 的取舍 |
| 改动作缩放不看 ctrlrange | 增量累积越界被 clip，节奏错乱 | `docs/experiment-log.md` 的实测 |
| 忽略 armature | 小步长下腿部抖动异常 | `models/go1/go1_mjx_position.xml` |
| 认为 trunk 也有执行器 | 12 个执行器里没有基座 | `models/go1/go1_mjx_position.xml,212-228` |
| 混淆 hip 类与髋 body | hip 类实际是 thigh 关节 | `models/go1/go1_mjx_position.xml,113,119` |
| 重排执行器顺序 | ctrlrange 切片与观测同时错 | `models/go1/go1_mjx_position.xml` 与 `envs/go1_walk.py` |
| 把 frictionloss 当阻尼 | 低速静差表现不同 | `models/go1/go1_mjx_position.xml` |

执行器段没有隐式映射：每个受控关节都要显式写一个 `<position>`，否则该关节只有重力和接触作用。

## 8. 小结

### 核心概念

1. freejoint 提供 6 自由度基座，12 个 hinge 各 1 自由度，qpos/qvel 布局 7+12 / 6+12。
2. `position` 执行器编译为固定增益与仿射偏置，关节力矩是 $k_p(ctrl-q)-k_v\dot q$ 再被 forcerange 夹。
3. ctrlrange 是动作空间边界，forcerange 是物理力矩上限，两者作用不同。
4. 走路用绝对目标，起身用增量目标，区别只在 env 的 step。
5. 关节 `damping`、`armature`、`frictionloss` 是关节自身的动力学，与伺服增益叠加。
6. 一次控制步含 10 个物理子步，ctrl 在子步之间保持不变。

### 设计权衡

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 位置伺服 + 绝对目标 | 与参考仓库逐位一致，任务窄易学 | 策略输出无界时容易瞬间甩到行程端点 |
| 位置伺服 + 增量目标 | 早期探索温和，适合起身 | 目标随当前角漂移，需额外锚定 |
| 换 torque 执行器 | 直接控制力矩，更接近真实电机 | 参考仓库的 position 策略不能直接迁移 |

基础题

1. 写出位置伺服编译后的力律，并说明 ctrlrange 与 forcerange 各自在哪一层夹紧。
2. 列出 hip、thigh、calf 三组执行器的 ctrlrange 与 forcerange，并指出小腿力矩上限更高的物理原因。
3. 说明 freejoint 与 hinge 在 qpos/qvel 里各占多少个分量，以及为什么 trunk 没有执行器。

挑战题

4. 把 `sim_dt` 从 0.002 改成 0.001 并保持 `ctrl_dt=0.02`，算出新的子步数，并说明这对伺服跟踪与接触稳定性分别有什么影响。
5. 走路早期版本把动作仿射映射到 ctrlrange。推导零动作对应的 hip 目标角，并说明它为什么会把初始策略的关节速度推到约 7 rad/s。

6. 从 `actuator_gainprm` 与 `actuator_biasprm` 反推 `kp`、`kv`，写出对应关系，并说明 `gear` 不为 1 时公式要怎样改写。
