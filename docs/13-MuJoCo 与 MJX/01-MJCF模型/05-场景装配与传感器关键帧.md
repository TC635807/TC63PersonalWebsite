# 场景装配、传感器与关键帧

主体 XML 只描述机器人，场景 XML 负责地面、光照与外观。两者用 `include` 拼接，编译后是同一个 MjModel。这条分离让平地与地形场景共用一份机器人定义，代价是资产路径与按名绑定都要成套维护。

`include` 与 `compiler` 决定资产路径的基准，写错一个相对路径会让两个场景共用同一份机器人定义时行为不同。hfield 的 `size` 四项与高度范围、14 个传感器在 `sensordata` 里的寻址范式，以及 keyframe 与 qpos/qvel 的维度差，是装配环节最容易接错的三处。

> 场景入口是 `models/go1/scene_mjx_position.xml` 与 `scene_mjx_terrain.xml`，传感器与关键帧在 `models/go1/go1_mjx_position.xml:230-249`，运行时读取在 `envs/go1_walk.py:447-448,472-473,549-559`。

## 1. 主体与场景的两段式装配

场景文件的四类内容：

| 段 | 作用 | 平地处 | 地形处 |
| --- | --- | --- | --- |
| `include` | 引入主体模型 | `scene_mjx_position.xml:2` | `scene_mjx_terrain.xml:33` |
| `statistic` | 查看器的视野中心与范围 | 第 4 行 | 第 35 行 |
| `visual` | 头灯、雾、默认视角 | 第 6-10 行 | 第 37-41 行 |
| `asset` | 天空盒、地面贴图、hfield | 第 12-17 行 | 第 43-68 行 |
| `worldbody` | 方向光与地面 geom | 第 19-24 行 | 第 70-87 行 |
| `light` | 方向光 | 第 20 行 | 第 71 行 |

主体模型里另外三个运行时常量：

| 段 | 内容 | 运行时读取 |
| --- | --- | --- |
| `sensor` | 14 个传感器 | `model.sensor_adr` / `sensor_dim` |
| `keyframe` | home 姿态与 ctrl | `mj_model.keyframe("home")` / `key_ctrl` |
| `option` | 接触锥与 impratio | `model.opt` |

场景与主体分离的直接收益是地面可替换：平地场景把 floor 写成 plane，地形场景换成 hfield，其余 body、sensor、keyframe 全部沿用同一份主体文件。两处 floor 都必须叫 floor，因为主体的接触传感器按名字绑定它。

```mermaid
  A --> W["worldbody: body 树与 floor geom"]
````

## 2. include、compiler 与 asset 的路径基准

`include` 在编译期展开，路径相对包含它的文件所在目录。主体里 `compiler` 的 `meshdir="assets"`（`models/go1/go1_mjx_position.xml:18`）生效于整个模型，mesh 与 hfield 的文件名都相对该目录解析。地形 PNG 由 `sim/gen_terrain.py` 生成到 `models/go1/assets/`，场景里只写 `file="terrain.png"`。

路径基准只有一处，因此移动或复制模型目录时要把 `assets/` 一起带走。运行时 `envs/go1_walk.py:415-419` 的 `update_assets` 收集 `*.xml` 与整个 `assets/` 目录放进字典，MJX 在 JIT 内重建模型时用同一份，不会回读本机路径。

asset 段里的资源分三类：mesh（STL）、texture/material（贴图与材质）、hfield（地形高度场）。三者在 MjModel 里都是固定大小数组，运行时不能替换。

## 3. hfield 的 size 四项与高度范围

hfield 的 `size` 是 `radius_x radius_y elevation_z base_z`。按场景注释的实测口径，geom 的高度范围是 $[pos.z,\ pos.z + elevation\_z + base\_z]$：

| 参数 | 本项目取值 | 作用 |
| --- | --- | --- |
| `radius_x` | 6 | 半宽 |
| `radius_y` | 6 | 半长 |
| `elevation_z` | 0.3000 | PNG 灰度的乘法系数 |
| `base_z` | 0.0960 | 只撑开几何包围盒 |

`base_z` 只撑开几何包围盒，地形形状全在 PNG 里，`elevation_z` 是 PNG 灰度的乘法系数。`base_z=0` 会被 MuJoCo 拒绝，所以取正的 0.0960。这条约束让"改 PNG 灰度"与"改 size"成为两件事：前者改形状，后者改采样系数与包围盒。

```mermaid
sequenceDiagram
  autonumber
  participant G as sim/gen_terrain.py
  participant P as assets/terrain.png
  participant X as scene_mjx_terrain.xml
  participant M as MjModel
  G->>P: 生成灰度高度场
  G->>X: 同步 elevation_z 与 base_z
  X->>M: hfield size 与 file
  M->>M: 采样高度 = 灰度 乘 elevation_z
````

## 4. 14 个传感器的三类分工

传感器输出拼在一维 `sensordata` 数组里，每个传感器有 `adr` 与 `dim`。运行时不直接按下标取，而是先查 `sensor(name).id`，再从 `sensor_adr` 拿偏移。Go1 的 14 个传感器分三类：

| 类 | 传感器名 | 维度 | 用途 |
| --- | --- | --- | --- |
| 本体 | `gyro`、`accelerometer`、本地 `local_linvel` | 3 各 | 角速度、加速度、机体系线速度 |
| 帧 | `global_linvel`、`global_angvel`、`upvector` | 3 各 | 世界系速度、姿态竖直分量 |
| 足端 | `{FR,FL,RR,RL}_global_linvel` | 3 各 | 足端速度，滑移惩罚 |
| 接触 | `{FR,FL,RR,RL}_floor_found` | 1 各 | 足-地接触，腾空时间 |

接触传感器写 `reduce="mindist" num="1" data="found" geom2="floor"`，输出是否发生接触。消费侧用 `> 0` 判布尔（`envs/go1_walk.py:956-959`）。

三类传感器对应三种观测需求：本体类给策略当前姿态与角速度，帧类给世界系速度与竖直方向，足端与接触类给步态相位与滑移判据。观测维度 48、83、91 的三个档位就是按这三类加不加区分出来的（`sim/view_go1.py:238-240`）。

## 5. sensordata 的寻址范式

```python
sid = mj_model.sensor(name).id
adr = mj_model.sensor_adr[sid]
dim = mj_model.sensor_dim[sid]
value = data.sensordata[adr:adr + dim]
```

`envs/go1_walk.py:447-448` 用 `site("imu").id` 定位观测参考点，`envs/go1_walk.py:549-559` 按 `sensor_adr`/`sensor_dim` 拼足端速度与接触。按名寻址的两个好处：改传感器顺序不会让观测错位，加传感器不会静默复用旧下标。


## 6. keyframe 与 qpos/qvel 的维度差

keyframe 只在编译时提供默认值。reset 会覆盖 qpos 的 xy、z 与四元数，但保留关节噪声；`key_ctrl` 用来初始化 ctrl 并叠加噪声（`envs/go1_walk.py:790-801`）。

qpos 与 qvel 的维度不同：位置态是 7 + 12 = 19，速度态是 6 + 12 = 18。reset 里 `qvel = jp.zeros(nv)` 先建全零，再写入前 6 维的随机根速度，剩下 12 维交给关节（`envs/go1_walk.py:802`）。观测里的 base 速度与关节速度因此都从 qvel 切片而来，切片上界要用 nv 而不是 nq。

| 数组 | 维数 | 组成 |
| --- | --- | --- |
| `qpos` | 19 | 基座 7 + 关节 12 |
| `qvel` | 18 | 基座 6 + 关节 12 |
| `ctrl` | 12 | 每个执行器一项 |
| `sensordata` | 按传感器累加 | 由 `adr`/`dim` 定位 |

传感器与 keyframe 是 XML 里少数被运行时反复读取的段，改动它们等于改环境接口，而不只是改模型外观。

## 8. 场景与传感器相关的故障现象

| 现象 | 原因 | 对应位置 |
| --- | --- | --- |
| 按 sensordata 下标硬取 | 改传感器顺序后观测错位 | `envs/go1_walk.py:549-559` 用 adr |
| 改 floor 名字 | 四个接触传感器失效 | `models/go1/go1_mjx_position.xml:241-244` |
| 只把 XML 加进 assets 字典 | JIT 内找不到 STL 或 PNG | `envs/go1_walk.py:415-419` 两个目录都要收 |
| 手动改 terrain.json 的 base_z 期望生效 | XML 的 base_z 是单独同步的 | `scene_mjx_terrain.xml:52-55` |
| 改 hfield 后不重测 pos.z | 出生点穿地或悬空 | `scene_mjx_terrain.xml:53-55` |
| 只复制 terrain.png 不复制 terrain.json | 复现时档位信息丢失 | `models/go1/assets/terrain.json` |
| 把 keyframe 当运行时状态 | 中途改动无效，reset 才读 | `envs/go1_walk.py:790` |
| 切地形场景却沿用平地观测维度 | 策略形状不符 | `sim/view_go1.py:238-240` 的 48/83 维区分 |
| 以为 hfield 的 base_z 改变地形 | 采样高度只乘 elevation_z | `scene_mjx_terrain.xml:53-55` |
| 把 qpos 维度当成 qvel 维度 | 速度切片越界 | `envs/go1_walk.py:802` |
| 以为 sensor 段可省 | 观测里没有 upvector 与接触信号 | `models/go1/go1_mjx_position.xml:230-245` |

## 9. 小结

### 核心概念

1. `include` 把主体与场景在编译期拼成一个 MjModel，路径相对各自文件。
2. `compiler` 的 `meshdir` 决定 mesh 与 hfield 的文件基准。
3. 传感器数据在 `sensordata` 一维数组里，按名字查到 `adr` 与 `dim` 再取。
4. 接触传感器输出布尔，靠 `geom2="floor"` 绑定地面，改名即断。
5. keyframe 是出生姿态与初始 ctrl 的单一来源，只在 reset 时读。
6. hfield 的 `base_z` 只撑包围盒，采样高度由灰度乘 `elevation_z` 决定。

### 设计权衡

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 主体与场景分文件加 include | 平地与地形共用一份机器人定义 | 资产要成套复制，路径基准是 meshdir |
| 传感器写在主体而不是 env | 物理与观测同一来源 | 改传感器要重编模型 |
| hfield 走 PNG 资产 | 训练与查看器加载同一份地形 | 需要 gen_terrain 同步 elevation_z 与 base_z |
