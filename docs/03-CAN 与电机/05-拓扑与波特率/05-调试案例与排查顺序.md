# 调试案例与排查顺序

工作记录 `can通信波特率问题.md` 记下一次 CAN 全体失效：底盘板的 CAN1 与 CAN2 都收不到报文，发送函数第一次返回 `HAL_OK`，之后一直返回 `HAL_ERROR`，假期前代码是正常的。记录给出的根因是时钟树被改动导致 APB1 频率变化。

这条链路需要完整复原一次，因为它包含一个反直觉的组合：位定时寄存器读回来完全正确，物理速率却错了 14.29%；发送函数的第一次调用成功，之后的调用持续失败。把这两个现象与 HAL 的分支结构、`AutoRetransmission` 的取值对上之后，排查顺序才能固定下来。下面按源码口径重建链路，修正记录里两处与头文件不符的描述，并整理一份可复用的排查顺序。

> 涉及的源码：云台板 `/home/wyx/rm/2026SentriOmeniGimbal/2026OmniSentryGimbal` 与底盘板 `/home/wyx/rm/2026SentriOmeniChassis/2026OmniSentryChassis`。两块板的 `Core/Src/can.c` 与 HAL 驱动相同，对应段落一致。工作记录位于 `/home/wyx/Work-Summary-and-Diary/工作记录/can通信波特率问题.md`。

## 三条寄存器读回值逐位解析

记录里用调试器读回的三个值：

| 寄存器 | 读回值 |
| --- | --- |
| `hcan2.ErrorCode` | 0x00200000 |
| MSR | 0x0C08 |
| TSR | 0x82000004 |

按 CMSIS 头文件与 HAL 头文件的位定义逐位解析：

| 值 | 位定义 | 含义 | 出处 |
| --- | --- | --- | --- |
| ErrorCode 0x00200000 | `HAL_CAN_ERROR_PARAM` | 最近一次失败的调用属于参数类失败 | `stm32f4xx_hal_can.h` |
| MSR 0x0C08 的 bit3 | `CAN_MSR_WKUI` | 唤醒中断挂起 | `stm32f407xx.h` |
| MSR 0x0C08 的 bit10 | `CAN_MSR_SAMP` | 最近一次采样点的电平 | `stm32f407xx.h` |
| MSR 0x0C08 的 bit11 | `CAN_MSR_RX` | CANRX 引脚电平 | `stm32f407xx.h` |
| TSR 0x82000004 的 bit2 | `CAN_TSR_ALST0` | 邮箱 0 仲裁失败 | `stm32f407xx.h` |
| TSR 0x82000004 的 bit25:24 | `CAN_TSR_CODE` | 值为 2，下一次请求使用邮箱 2 | `stm32f407xx.h` |
| TSR 0x82000004 的 bit28:26 | `CAN_TSR_TME2` 到 `TME0` | 全为 0，三个发送邮箱都没有空位 | `stm32f407xx.h` |
| TSR 0x82000004 的 bit31 | `CAN_TSR_LOW2` | 邮箱 2 处于最低优先级 | `stm32f407xx.h` |

三个值组合起来指向同一件事：有帧想发、邮箱全满、总线上的电平不对。`ALST0` 说明邮箱 0 曾参与仲裁但失败，`TME` 全 0 说明三个邮箱都被占着，`SAMP` 与 `RX` 给出的是引脚上的瞬时电平，不构成总线正常工作或异常的直接结论。

## 记录文字与头文件的两处偏差

记录的文字描述里有两处与头文件对不上，按源码口径更正：

| 记录里的写法 | 源码口径 |
| --- | --- |
| 0x00200000 等于 `HAL_CAN_ERROR_NOT_STARTED` | 0x00200000 是 `HAL_CAN_ERROR_PARAM`；`NOT_STARTED` 是 0x00100000（`stm32f4xx_hal_can.h`） |
| MSR 0x0C08 表示 ERRI 挂起 | ERRI 是 MSR 的 bit2，0x0C08 的 bit2 为 0；置位的是 bit3、bit10 与 bit11 |

`HAL_CAN_ERROR_NOT_STARTED` 的产生点在 `HAL_CAN_Stop()` 里（`stm32f4xx_hal_can.c`），与本次现象无关。

两处偏差的性质相同：用数值去猜宏名的含义。0x00200000 与 0x00100000 都是“某一位被置起”，在没有对照头文件时容易记混；MSR 的 `ERRI` 与 `WKUI` 相邻但不同位。排查时把数值与位定义一起抄下来，比只记一个宏名可靠。

## 第一次 HAL_OK、之后一直 HAL_ERROR 的机制

`HAL_CAN_AddTxMessage` 的结构决定了这两种返回值来自不同分支（`Drivers/STM32F4xx_HAL_Driver/Src/stm32f4xx_hal_can.c`）：

1. 先判断外设状态必须是 `READY` 或 `LISTENING`。
2. 读一次 TSR，检查三个 `TME` 位里是否有任意一位为 1。有一位为空，就填入该邮箱、置请求位并返回 `HAL_OK`。
3. 三个邮箱都满时，走 `else` 分支，把 `ErrorCode` 或上 `HAL_CAN_ERROR_PARAM` 并返回 `HAL_ERROR`。
4. 状态不满足时，或上 `HAL_CAN_ERROR_NOT_INITIALIZED`。

因此读到的 0x00200000 只能来自第 3 步，也就是三个邮箱全满。把这条约束与 `AutoRetransmission` 的取值放在一起，现象就能还原。两块板的 `AutoRetransmission` 都是 `ENABLE`（`Core/Src/can.c`），发送失败或未获应答的帧会留在邮箱里自动重发。

对应的分支结构如下：

```c
/* 简化：HAL_CAN_AddTxMessage 的两个返回值分支 */
if (state != READY && state != LISTENING) return HAL_ERROR;  /* ErrorCode 或上 NOT_INITIALIZED */
for (i = 0; i < 3; i++) {
    if (tsr & (CAN_TSR_TME0 << i)) {                          /* 找到空邮箱 */
        fill_mailbox(i); set_TXRQ(i);
        return HAL_OK;                                       /* 第一次调用走这里 */
    }
}
ErrorCode |= HAL_CAN_ERROR_PARAM;                            /* 三个邮箱全满：0x00200000 */
return HAL_ERROR;
```

```mermaid
sequenceDiagram
  autonumber
  participant APP as 控制任务
  participant HW as bxCAN
  participant BUS as 总线
  participant PEER as 对端节点
  APP->>HW: HAL_CAN_AddTxMessage 第一帧
  HW->>BUS: 按错误的位速率发出
  Note over BUS: 位宽与对端不一致 对端判为错误 不应答
  PEER--xBUS: 应答槽保持隐性
  HW->>HW: 应答错误 发送错误计数加 8
  Note over HW: AutoRetransmission 为 ENABLE 该帧留在邮箱重发
  APP->>HW: 第二帧
  HW-->>APP: 三个邮箱都不空 返回 HAL_ERROR
  HW->>HW: ErrorCode 或上 0x00200000
  APP->>HW: 后续每一帧
  HW-->>APP: 一直返回 HAL_ERROR
```

第一次进邮箱是软件动作，与总线状态无关，所以返回 `HAL_OK`。之后失败是因为第一帧占着邮箱不肯离开。这一条也解释了为什么“第一次发送成功”不能当成通信可用的证据。

## 857143 bps 与 14.29% 的偏差

记录给出的根因是时钟树配置被修改，APB1 频率随 `RCC.APB1CLKDivider` 与 PLL 参数变化。位定时参数不动时，把 PCLK1 从 42 MHz 换成 36 MHz：

$$TQ = \frac{2}{36 \times 10^{6}} = 55.556\ \text{ns}$$

$$t_{bit} = 21 \times 55.556\ \text{ns} = 1166.67\ \text{ns}$$

$$f_{baud} = \frac{1}{1166.67\ \text{ns}} = 857143\ \text{bps}$$

与目标 1 Mbps 相差 14.29%。记录里写的计算波特率 857142 Hz 与这个数值一致，说明当时的 PCLK1 约为 36 MHz。仓库当前的两份 `Core/Src/can.c` 位定时参数相同，ioc 的 `RCC.APB1Freq_Value` 也都是 42000000（云台板 `2026sentriomeni.ioc`，底盘板同名文件），修复已经落到代码里。

偏差的计算过程可以复用一个比值：位定时参数不变时，波特率与 PCLK1 成正比，因此偏差等于频率之比，$42/36 - 1 = 16.67\%$（按频率看），而按波特率看是 $1 - 36/42 = 14.29\%$。两个百分数描述的是同一件事，取哪个取决于基准取谁。

## 为什么 CAN1 与 CAN2 同时失效

两个 bxCAN 控制器都挂在 APB1 上，共用同一个 PCLK1。时钟树改动会影响两个控制器的实际位速率，因此 CAN1 与共享段上的对端板、CAN2 与四个轮子同时失去通信。这一点是判断根因在时钟树而非单条总线接线的重要依据：一条总线的故障通常只影响一条。

反过来说，如果只有一条 CAN 失效，就可以先从时钟树这一项里排除出去。这条推论在第 7 题里会用到。

## 按源码口径整理的排查顺序

记录给出的优先级是时钟、GPIO 复用、外设初始化顺序、中断、物理层、应用逻辑。按前两节的推导，这个顺序对本工程成立，其中第 1 项与第 2 项的判断依据如下：

```mermaid
flowchart TD
  S["CAN 收发异常"] --> Q1{"HAL_RCC_GetPCLK1Freq<br/>是否为 42 MHz"}
  Q1 -- "否" --> F1["时钟树被改动<br/>核对 ioc 的 RCC 键并重新生成"]
  Q1 -- "是" --> Q2{"两块板的 BTR<br/>是否都为 0x004E0001"}
  Q2 -- "否" --> F2["位定时参数被改动<br/>比对两份 can.c"]
  Q2 -- "是" --> Q3{"ErrorCode 是否为 0x00200000"}
  Q3 -- "是" --> F3["发送邮箱被占满<br/>查 AutoRetransmission 与应答缺失"]
  Q3 -- "否" --> Q4{"总线上是否有差分波形"}
  Q4 -- "否" --> F4["物理层<br/>接线 终端电阻 收发器供电"]
  Q4 -- "是" --> F5["查 GPIO 复用 初始化顺序 中断与过滤器"]
```

时钟树排在第一位的原因：BTR 的值不会随时钟树变化，读回来仍是 `0x004E0001`，而物理速率已经错了。寄存器正确、速率错误这一组合是本次最难判断的地方。把 `HAL_RCC_GetPCLK1Freq()` 的返回值放在 BTR 之前核对，就能一步跳过这个组合。

## 记录里可复用的证据清单

这条案例留下的证据可以按用途分成三类，后面遇到类似故障时按同一张表取数：

| 证据 | 取值 | 用途 | 局限 |
| --- | --- | --- | --- |
| 两次调用的返回值 | 第一次 `HAL_OK`、之后 `HAL_ERROR` | 区分入队失败与总线失败 | 只说明邮箱状态，不说明总线 |
| `ErrorCode` | 0x00200000 | 指向"参数类失败"，即邮箱全满分支 | 与真实根因隔了一层 |
| MSR | 0x0C08 | 提供引脚电平与唤醒状态 | 与波特率无关 |
| TSR | 0x82000004 | 邮箱占用与仲裁失败 | 与时钟树无关 |
| 计算波特率 | 857142 Hz | 与 36 MHz 的 PCLK1 自洽 | 需要与目标值比较才有意义 |

单独看任何一个值都得不到结论：`ErrorCode` 指向邮箱，TSR 指向邮箱，MSR 指向引脚，只有把它们与“BTR 正确”这一条放在一起，才能定位到时钟树。

## 小结

### 核心概念

- 0x00200000 是 `HAL_CAN_ERROR_PARAM`，来自 `HAL_CAN_AddTxMessage` 三个邮箱全满的分支；`NOT_STARTED` 是 0x00100000。
- TSR 0x82000004 表示邮箱 0 仲裁失败、三个邮箱都没有空位、下一次请求指向邮箱 2。
- MSR 0x0C08 的 bit2 为 0，记录的 ERRI 结论与位定义不符；置位的是 bit3、bit10 与 bit11。
- `AutoRetransmission` 为 `ENABLE` 时，未获应答的帧留在邮箱重发，后续发送全部返回 `HAL_ERROR`。
- 两个控制器共用 PCLK1，时钟树改动会让 CAN1 与 CAN2 同时失效。
- 排查顺序里时钟树排在第一位，因为 BTR 值正确并不说明物理速率正确。

### 设计权衡

| 权衡点 | 本工程的选择 | 代价与收益 |
| --- | --- | --- |
| 根因定位 | 记录按时钟、GPIO、初始化、中断、物理层、逻辑排序 | 覆盖了共享 PCLK1 这一层；代价是每一步都要读寄存器，耗时长 |
| 错误码使用 | 记录用数值记错误码 | 排查时信息集中；代价是数值与文字对不上时容易被误导 |
| 自动重传 | `ENABLE` | 偶发仲裁失败能自恢复；代价是速率错误时现象具有误导性 |
| 返回值处理 | 调用点不接收 | 代码简洁；代价是持续失败不可见 |
| BTR 核对 | 期望值 `0x004E0001` | 一眼可比对；代价是时钟树变化不在这个寄存器里体现 |
