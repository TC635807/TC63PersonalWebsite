# 零点与多圈角度

同一个“角度”在固件里至少对应三种量：电调给出的单圈机械角、主控自己拼出来的累计角度、姿态解算内部的姿态零点。三者零点不同、生命周期不同，混用会得到差一个常数的结果，而且这个常数随上电时机变化。

反馈帧只带单圈信息，超过一圈的部分必须由主控累加，累加逻辑的核心是一个半圈判据。要说明的是判据怎么工作、它什么时候会失效、底盘板的 16 位累计角度为什么只能撑约正负 4 圈，以及三个零点分别在哪一刻被定下来。读完后应当能在调试器里分清 `round_count`、`total_angle` 与 `yaw_zero` 三个量各代表什么。

## 三种零点与两种一圈

| 名称 | 定义位置 | 取值范围 | 断电是否保留 |
| --- | --- | --- | --- |
| 单圈机械角 | 电调内部，随电机转动 | 0 到 8191 | 保留，由转子位置决定 |
| 累计角度 | 主控每次收到反馈时更新 | 由圈数与单圈值拼出 | 不保留，上电重新开始 |
| 姿态零点 | 姿态解算内部，上电后第一次采样确定 | 相对值 | 不保留 |

“一圈”也对应两种周期：编码器的一圈是 8192 计数，姿态角的一圈是 360 度。角度环的两个入口在前一篇，这里处理的是这些零点从哪来、多圈怎么拼、拼出来能存多少。

单圈机械角由电调在出厂时标定，掉电后仍然有效，这是唯一一个与机械结构绑定的量。累计角度和姿态零点都是上电后才产生的软件量，重启一次就重新开始，因此两份绝对角度只在同一次上电内可比。

## 半圈判据怎么拼出连续角度

拼接函数 `update_motor_total_angle`（云台板 `BSP/Src/bsp_can.cpp:557-585`、底盘板 `BSP/Src/bsp_can.cpp:520-548`）只有三段逻辑：

```c
void update_motor_total_angle(DJI_motor_info* motor, uint16_t new_ecd)
{
    if (!motor->inited) {                       /* 首次收到反馈 */
        motor->last_angle  = new_ecd;
        motor->round_count = 0;
        motor->total_angle = (int32_t)new_ecd;
        motor->inited = 1;
        return;
    }
    int32_t diff = (int32_t)new_ecd - (int32_t)motor->last_angle;
    if (diff > 4096)       { motor->round_count--; }   /* 反向跨过零点 */
    else if (diff < -4096) { motor->round_count++; }   /* 正向跨过零点 */
    motor->total_angle = motor->round_count * 8192 + (int32_t)new_ecd;
    motor->last_angle  = new_ecd;
}
```

判据是相邻两次反馈的计数差是否超过半圈。转子在两帧之间不可能转过超过半圈，所以差值超过 4096 只能解释为跨过了零点，跨的方向由差值的符号给出。这个前提写成公式就是转速上限：

$$n_{\max} = \frac{4096 \times 60}{8192 \times T} = \frac{30}{T}$$

$T$ 是反馈帧的到达间隔，单位秒。取 $T = 1\ \text{ms}$ 时 $n_{\max}$ 为 30000 转每分钟，高于直驱电机与减速电机的实际转速上限，判据是安全的。本仓库里找不到反馈周期的明确定义，这一条标注为待实测。

首次收到反馈时 `inited` 被置 1，`round_count` 清零，`total_angle` 直接等于当次的单圈计数。这个动作把累计角度的原点定在了“第一帧到达时的转子位置”，而不是机械零位。

```mermaid
stateDiagram-v2
    [*] --> 首次
    首次 --> 正常: 记录 last_angle 与 total_angle<br/>round_count 置 0
    正常 --> 正向跨零: 差值小于负 4096<br/>round_count 加一
    正常 --> 反向跨零: 差值大于正 4096<br/>round_count 减一
    正常 --> 正常: 差值落在正负 4096 内
    正向跨零 --> 正常: total_angle 等于 round_count 乘 8192 加新计数
    反向跨零 --> 正常: 同上
```

## 用两个数值验证方向，并核对注释

上一帧计数 8000、本帧 200，差值为负 7800，判为正向跨零，圈数加一，累计角度为 $8192 + 200 = 8392$。上一帧 200、本帧 8000，差值为正 7800，判为反向跨零，圈数减一，累计角度为 $-8192 + 8000 = -192$。两种情况的累计角度都连续，判据方向正确。

代码注释在这里与实现不一致：注释写的是“向上跨过 0 点，round_count 增加”，而代码在差值为负（正向跨零）时才增加圈数。按指南的口径以代码为准，注释按字面理解会把方向写反。这一条属于文档与代码的冲突，调试时以 `round_count` 的实际增减为准。

判据的另一个性质是它只依赖相邻两帧。中间丢帧时差值会变大，只要仍小于半圈就不会误判；一旦丢帧时间长到转子转过超过半圈，就会多算或少算一圈，而代码里没有任何补偿。

姿态零点在 `Task/Src/ImuTask.cpp:26` 声明、`Task/Src/ImuTask.cpp:65-70` 确定：

if(first_run) { yaw_zero = yaw; first_run = false; }
yaw_out = yaw - yaw_zero;

底盘侧的零点在底盘板 `Task/Src/ControlCenterTask.cpp:49-51` 确定，比电机侧晚一步，因为要等 100 ms 让 CAN 收到第一批反馈（延时在 `Task/Src/ControlCenterTask.cpp:49`）：

Init_yaw_counts = yaw_motor_5.total_angle;

## 云台板算了却没用的多圈角度

云台板的 `DJI_motor_info` 里 `total_angle` 是 `int16_t`（云台板 `BSP/Inc/bsp_can.h:17`），只有 0x205 与 0x206 两路会调用拼接函数（云台板 `BSP/Src/bsp_can.cpp:623`、`BSP/Src/bsp_can.cpp:634`）。写入之后，`motor_5.total_angle` 与 `motor_6.total_angle` 在整个仓库里都没有读取点：唯一提到它的那一行是注释（`Task/Src/GimbalTask.cpp:70`），拨盘环用的是 `motor_6.rotor_speed` 而不是累计计数（`Task/Src/FireTask.cpp:53`、`Task/Src/FireTask.cpp:56`）。云台板把累计角度算了出来，却没有任何控制回路消费它。

云台板在用的多圈量在姿态那一侧：`gimbal_yaw_total` 由每帧 yaw 差分累加（`Task/Src/ImuTask.cpp:77-94`），累加时用正负 180 度判据处理跨零（`Task/Src/ImuTask.cpp:87-91`），最终写入 `imu_data.gimbal_yaw_total_angle`（`Task/Src/ImuTask.cpp:100`）。这条路径是活跃的，与电机编码器的累计角度互不相干。

## 底盘板的 16 位累计角度与 3100 偏移

两块板的结构体里 `total_angle` 都是 `int16_t`（云台板 `BSP/Inc/bsp_can.h:17`、底盘板 `BSP/Inc/bsp_can.h:17`），而拼接表达式是 `round_count * 8192 + new_ecd`（云台板 `BSP/Src/bsp_can.cpp:581`、底盘板 `BSP/Src/bsp_can.cpp:544`）。赋值时高 16 位被截掉，等价于对 65536 取模后再按有符号解释：

$$\text{total\_angle} \in [-32768,\ 32767] \Rightarrow |\text{圈数}| \le \frac{32767}{8192} \approx 4$$

底盘跟随角度依赖这个值。此后每个周期用初值减去当前读数得到相对角（底盘板 `Task/Src/ControlCenterTask.cpp:93-94`），再参与底盘与云台坐标系的旋转补偿（底盘板 `Task/Src/ControlCenterTask.cpp:109-110`）：

$$\Delta\theta = (\text{Init\_yaw\_counts} - \text{total\_angle}) \times \frac{2\pi}{8192}$$

$3100$ 是硬编码的机械零位偏移（底盘板 `Task/Src/ControlCenterTask.cpp:51`），代码与仓库文档里都没有说明它的来源，标注为待核实。可以确定的是它参与的是初值计算而不是每周期计算，改它会整体平移底盘的参考方向。

底盘板还有一处只用单圈值的换算（底盘板 `Task/Src/UsbConnectTask.cpp:171`，`mapToAngle` 定义在 `Task/Src/UsbConnectTask.cpp:208-211`）：

```cpp
only_yaw.yaw = mapToAngle(yaw_motor_5.rotor_angle) - 180;   /* 系数 180/4096 */
```

`rotor_angle` 取 0 到 8191，乘以 $180/4096$ 得到 0 到 360 度，减去 180 后落在正负 180 度内。这是把单圈计数直接映射成罗盘角的做法，不依赖累计角度，所以不受 16 位回绕影响。

## 判据失效的边界

半圈判据的成立条件只有一条：两次反馈之间转子转过不超过半圈。把条件反过来写就得到失效的边界：

| 反馈间隔 $T$ | 转速上限 $n_{\max}$ | 相对实际转速的裕量 |
| --- | --- | --- |
| 1 ms | 30000 转每分钟 | 裕量充足 |
| 2 ms | 15000 转每分钟 | 仍高于多数电机上限 |
| 4 ms | 7500 转每分钟 | 对高转速电机已经不够 |

裕量随间隔线性下降，所以风险主要来自丢帧而不是正常周期。总线错误、电调上电抖动、任务长时间关中断都会让间隔被拉长，间隔一旦超过半个转子圈对应的时长，圈数就会算错一格，此后的累计角度永久偏移 8192。

需要补偿时的做法是引入转速判据：用上一帧的 `rotor_speed` 估计本帧应该跨过多少圈，与半圈判据的结果比对，不一致时按转速估计修正。代价是转速本身也有噪声，需要额外的滤波。

## 异常现象对照

| 现象 | 可能原因 | 检查手段 |
| --- | --- | --- |
| 上电位置不同，跟随角差一个常数 | 首次反馈决定累计角度原点 | 记录首次反馈时的单圈计数 |
| 转过多圈后跟随角突然跳变 | 底盘板 16 位累计角度回绕，约正负 4 圈 | 调试器里同时看 `round_count` 与 `total_angle` |
| 累计角度增长方向与转向相反 | 注释与代码方向相反时按注释修改 | 以 `round_count` 的实际增减为准 |
| 断电重启后绝对角度丢失 | 累计角度只用内存保存 | 需要绝对角度时增加上电回零动作 |
| 电机停转后角度仍在缓慢变化 | 没有接收超时判定，中断不再来则字段保持旧值 | 加时间戳或到达计数 |
| 姿态零点与机械零点混用 | 两个零点在不同任务里各自确定 | 统一到同一参考系后再比较 |

## 小结

### 核心概念

- 单圈机械角由电调给出，累计角度由主控用半圈判据自行拼接，两者的零点不同。
- 半圈判据的安全上限是 $n_{\max} = 30/T$，在 1 ms 反馈间隔下为 30000 转每分钟。
- 首次反馈把累计角度的原点定在上电时的转子位置，因此绝对角度在不同上电之间没有可比性。
- 两块板的累计角度都是 16 位，可用范围约正负 4 圈，超出后回绕。
- 姿态零点由上电后第一次姿态解算确定，与编码器零点无关，云台板的 yaw 环只用前者。
- 云台板把 `motor_5.total_angle` 算了出来却没有使用，拨盘电机是唯一使用累计计数的角度环。

### 设计权衡

| 选择 | 本工程的做法 | 代价与收益 |
| --- | --- | --- |
| 累计角度位宽 | 两块板都用 16 位 | 结构体紧凑；代价是超过 4 圈即回绕 |
| 零点确定时机 | 首次反馈与首次姿态解算各自确定 | 无需上电回零；代价是三个零点互不相关 |
| 过零判据 | 固定 4096 计数阈值 | 实现简单；代价是长间隔丢帧后可能误判 |
| 机械零位 | 硬编码 3100 计数 | 改动一处即可调整；代价是含义只能从数值猜 |
| 单圈映射 | 单圈计数乘 180/4096 再减 180 | 直接得到罗盘角；代价是丢失多圈信息 |

## 练习

### 基础题

1. 上一帧计数为 100，本帧为 8100，写出 `round_count` 的增减、`total_angle` 的值，并判断转子转向。
2. 反馈周期为 2 ms，计算半圈判据允许的最大转速；若电机以 6000 转每分钟运行，判据是否会误判。
3. 底盘板 `round_count` 为 5、单圈计数为 1000 时，写出表达式结果与截断后的 `total_angle`，并说明与真实累计角度差多少。
4. 说明为什么首次反馈要单独判断 `inited`，而不是直接用 `last_angle` 的初值 0 参与差分。

### 挑战题

5. 把 `total_angle` 改成 32 位，说明需要同步修改哪些类型、初始化与比较表达式，并给出一次跨越 4 圈的验证方案。
6. 设计一个上电回零流程：让 yaw 关节在限速下缓慢转到机械限位，把该位置的计数写入非易失存储，之后每次上电用它恢复绝对零点，并说明断电发生在回零过程中的处理办法。
7. 用 4096 之外的阈值做一个对比实验：给定反馈丢帧时长与转速，推导最优阈值，并说明为什么本工程用固定阈值仍可接受。
